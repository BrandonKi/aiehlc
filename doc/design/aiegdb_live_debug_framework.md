# aiegdb Live Debug Framework

How the browser schedule viewer drives a live, stateful `aiegdb` debug console
against a real AIE board. This document traces the **whole round trip**: from a
keystroke in `host_schedule.html`, through the local HTTP daemon, into the
persistent `aiegdb.py` REPL subprocess, down through `aiediag.py` and `aiedbg`,
across JTAG to the board — and back.

Companion doc: [`live_debug_framework.md`](live_debug_framework.md) (the broader
run/applog/grid framework). This doc focuses on the **aiegdb console** tier.

---

## 1. The tiers at a glance

Everything except the board runs on `localhost` (the daemon binds `0.0.0.0` by
default so another machine on the LAN can open the page, but all subprocesses are
local to the daemon host).

```
┌─────────────────────────────────────────────────────────────────────────┐
│  Browser  —  host_schedule.html  (generated by schedule_view.py)          │
│    #cmdconsole terminal:  type "target tile 0 3", "dma status", "?", ...   │
│    clicks on a tile/channel also drive the console                         │
└───────────────┬───────────────────────────────────────────────────────────┘
                │  HTTP POST /aiegdb  {cmd:"dma status"}   (JSON, fetch)
                │  HTTP POST /aiegdb/reload                (kill+respawn)
                v
┌─────────────────────────────────────────────────────────────────────────┐
│  Daemon  —  schedule_debug_server.py   (stdlib http.server, 127.0.0.1)     │
│    DebugState holds ONE long-lived aiegdb subprocess + a reader thread     │
│    gdb_command(): write cmd to stdin, read stdout up to _SERVER_MARKER     │
└───────────────┬───────────────────────────────────────────────────────────┘
                │  subprocess stdin/stdout pipes (text, line-buffered)
                │  framed by _SERVER_MARKER = "\x1e@AIEGDB@ <scope>"
                v
┌─────────────────────────────────────────────────────────────────────────┐
│  REPL  —  aiegdb.py --server   (persistent Python process)                 │
│    AieGdb scope stack: partition → tile → channel                          │
│    serve_stdin(): one cmd per line, run_line(), emit marker w/ new scope   │
│    imports aiediag.py as a library (offsets, decoders, provenance)         │
└───────────────┬───────────────────────────────────────────────────────────┘
                │  subprocess:  aiedbg --json --target xsdb://.. -d pal reg read ..
                v
┌─────────────────────────────────────────────────────────────────────────┐
│  aiedbg  →  xsdb  →  hw_server @ xxx.xxx.xxx.213:3121 (JTAG)  →  board (AIE)  │
└─────────────────────────────────────────────────────────────────────────┘
```

**Why a persistent subprocess?** `aiegdb` is a *stateful* REPL — its current
scope (partition/tile/channel) determines how the next command is interpreted
(`dma status` at channel scope auto-injects `phys_col`, `row`, `dir/ch`). HTTP is
stateless, so the daemon keeps **one** `aiegdb.py --server` process alive and
feeds it commands over a pipe, preserving scope between requests.

## 2. Tier 1 — the browser console (`schedule_view.py` → `host_schedule.html`)

`schedule_view.py` generates the static HTML/JS. The bottom-right `#cmdconsole`
is a small terminal: an output pane plus an input line whose prompt shows the
current aiegdb scope.

### 2.1 Sending a command

All calls go through one helper (`schedule_view.py:1113`):

```js
function api(path, opts){ return fetch(path, opts).then(r => r.json()); }
```

`conSend()` (`schedule_view.py:1039`) echoes the typed line, POSTs it to
`/aiegdb`, appends the returned `output`, and updates the breadcrumb from the
returned `scope`:

```js
function conSend(cmd, echo, applyScope){
  if (echo !== false) conAppend(CON.scope + '> ' + cmd);
  return api('/aiegdb', {method:'POST',
                         headers:{'Content-Type':'application/json'},
                         body: JSON.stringify({cmd})})
    .then(r => { if (r.output) conAppend(r.output);
                 if (r.scope)  conSetScope(r.scope); })
    .catch(() => conAppend('daemon offline (static mode)'));
}
```

The daemon reply is always `{"output": "...", "scope": "partition/tile(0,3)/..."}`.
The `scope` field is what keeps the browser breadcrumb in sync with the REPL's
real state — the browser never guesses the scope, it echoes what the REPL reports.

### 2.2 Clicks drive the console too

Clicking a tile/channel calls `setConTarget(t, ch)` (`schedule_view.py:1061`),
which just synthesizes the same navigation commands a user could type:

```js
const p = conSend('target tile ' + t.loc[0] + ' ' + t.loc[1], undefined, !ch);
if (ch) p.then(() => conSend('target channel ' + ...));   // chain to channel
```

So a click and a keystroke take the identical path — there is no second protocol.

### 2.3 Reload button

`#conreload.onclick` (`schedule_view.py:1088`) POSTs `/aiegdb/reload`; on success
it prints `[reloaded aiegdb.py]` and resets the breadcrumb to the fresh scope
(partition). This is how edits to `aiegdb.py`/`aiediag.py` take effect without
restarting the daemon.

### 2.4 Lazy spawn on connect

`testConnect()` (`schedule_view.py:1202`), after a successful `/ping`, calls
`conSend('', false)` — an empty, non-echoed command whose only purpose is to make
the daemon spawn the aiegdb subprocess and report the real starting scope (e.g.
`partition(startcol=3)`), so the prompt is correct before the user types anything.

## 3. Tier 2 — the daemon (`schedule_debug_server.py`)

A stdlib `ThreadingHTTPServer` (`main()`, `:909`). It imports `aiediag` and
`aiegdb` as libraries (both guard `main()` behind `__main__`, so importing has no
side effects). From `aiegdb` it needs only the framing constant `_SERVER_MARKER`.

### 3.1 Routes

`Handler.do_POST` (`:728`) adds two routes for the console:

| Route                 | Handler                        | Notes |
|-----------------------|--------------------------------|-------|
| `POST /aiegdb`        | `st.gdb_command(body["cmd"])`  | No `_hw_available` hard-gate — navigation/`help`/`?` work with no board; live reads fail gracefully *inside* aiegdb. |
| `POST /aiegdb/reload` | `st.gdb_reload()`              | Terminate + respawn the subprocess; returns fresh `scope`. |

The legacy `/cmd` route (a fixed op-whitelist of structured reads) is still
present but no longer used by the console; `/aiegdb` supersedes it.

### 3.2 The persistent subprocess

`DebugState` (`:82`) owns the subprocess and serializes access with
`self._gdb_lock` (`:110`), so a slow `aiedbg` read only blocks the console — not
`/applog` or `/grid` polling (those run on other threads).

**Spawn** — `_gdb_spawn()` (`:275`) builds the command from the daemon's own
config and starts a reader thread:

```python
cmd = [sys.executable, "-u", self.aiegdb, "--server",
       "--startcol", str(self.startcol), "--device", self.device,
       "--aie-version", str(self.aie_version), "--json-dir", self.workdir]
if self.target:
    cmd += ["--target", self.target]
self._gdb_proc = subprocess.Popen(cmd, stdin=PIPE, stdout=PIPE,
                                  stderr=STDOUT, text=True, bufsize=1)
# reader thread: for line in proc.stdout: q.put(line); then q.put(None) on EOF
```

`--json-dir self.workdir` is what lets the REPL's `channels`/`bd` commands find
the provenance JSONs. `-u` (unbuffered) + `bufsize=1` keep the pipe responsive.
The startcol/aie-version the daemon passes are themselves auto-detected from the
provenance JSONs in the workdir (`main()`, `:896`) unless overridden by flags.

**Read** — `_gdb_read_until_marker()` (`:299`) pulls lines from the queue,
accumulating non-marker lines. When it sees a line starting with `_SERVER_MARKER`
it strips the prefix, records the remainder as `self._gdb_scope`, and returns the
accumulated text. On EOF (`None`) or a `queue.Empty` timeout it returns what it
has plus an error note and marks the proc dead (`_gdb_proc = None`).

**Command** — `gdb_command(cmd)` (`:320`), under the lock: respawn if the proc is
dead, write `cmd + "\n"` to stdin, flush, then read up to the marker. Returns
`{"output": _strip_ansi(out), "scope": self._gdb_scope}`. `_strip_ansi` (`:59`)
is defensive only — piped stdout is not a tty, so `aiediag._USE_COLOR` is already
off and no ANSI codes are emitted.

**Reload** — `gdb_reload()` (`:335`), under the lock: `terminate()`, short
`wait`, `kill()` if needed, then `_gdb_spawn()` — a fresh Python process that
re-imports the edited `aiegdb.py`/`aiediag.py`, landing at partition scope.

On daemon shutdown (`KeyboardInterrupt`, `:934`) the subprocess is terminated.

## 4. Tier 3 — the REPL (`aiegdb.py --server`)

`--server` (`main()`, `:783`) builds the `AieGdb` object as usual, then calls
`serve_stdin()` (`:735`) instead of the interactive loop:

```python
def serve_stdin(self):
    def emit_marker():
        sys.stdout.write(_SERVER_MARKER + self.prompt().rstrip() + "\n")
        sys.stdout.flush()
    emit_marker()                      # initial scope
    for raw in sys.stdin:
        line = raw.rstrip("\n")
        try:
            keep_going = self.run_line(line)   # normal REPL dispatch
        except Exception as e:                 # a bad command must not kill it
            print(f"error: {e}"); keep_going = True
        sys.stdout.flush()
        emit_marker()                  # marker's remainder = new prompt/scope
        if keep_going is False:
            break
```

Key properties:

- **`_SERVER_MARKER = "\x1e@AIEGDB@ "`** (`:48`) — the `\x1e` record-separator
  prefix never appears in normal output, so the daemon can unambiguously detect
  the end of a command's output and read the new scope from the same line.
- **The dispatch is unchanged** — `serve_stdin` reuses `run_line()` verbatim, so
  the console gets the exact same commands as the interactive CLI: `target`,
  `up`/`top`, `dma status`, `bd`, `event`, `pc`, `dma counter`, `reg read`,
  `help`, and `?` (which lists just the current scope's commands).
- **Scope is preserved** across commands because the single process holds the
  `AieGdb` scope stack (`self.tile`, `self.channel`) between stdin lines.

## 5. Tier 4 — aiediag → aiedbg → board

`aiegdb` does not talk to hardware directly. It imports `aiediag.py` for the
register offsets, decoders, provenance maps, and the `run_aiedbg_reg_read()`
helper, and for raw passthroughs it shells out to `aiedbg -d <device>`.

`aiediag.run_aiedbg_reg_read(phys_col, row, off, target=.., device=..)` runs, e.g.:

```
aiedbg --json --target xsdb://xx.xx.xx.213:3121 --device pal reg read 3 3 0x1DF10
```

`aiedbg` connects through `xsdb` to the JTAG `hw_server` and reads the AIE array.
The result flows back up: raw value → aiediag decoder → aiegdb prints decoded text
→ marker line → daemon returns `{output, scope}` → browser appends to the console.

Reads are **read-only** by default (the only write path in aiegdb is the explicit
`dma counter setup`), so the console cannot disturb a running board while
`apppaltest -nonreboot` holds the primary xsdb session on the same JTAG bridge.

## 6. End-to-end example: `dma status` on tile(0,3)/mm2s0

1. User clicks tile (0,3), then channel `mm2s0` (or types the two `target`
   commands). Browser POSTs `/aiegdb {cmd:"target tile 0 3"}` then
   `{cmd:"target channel mm2s0"}`, then the user types `dma status`.
2. Daemon `gdb_command("dma status")` writes `dma status\n` to the subprocess
   stdin and blocks on `_gdb_read_until_marker()`.
3. REPL `run_line("dma status")` at channel scope resolves
   `phys_col = 0 + startcol(3) = 3`, `row = 3`, `mm2s0` → offset `0x1DF10`, and
   calls `aiediag.run_aiedbg_reg_read(3, 3, 0x1DF10, ...)`.
4. `aiedbg --json --target .. -d pal reg read 3 3 0x1DF10` reads the board;
   aiediag decodes the status word; aiegdb prints the decoded lines, then
   `\x1e@AIEGDB@ partition(startcol=3)/tile(0,3)/mm2s0>`.
5. Daemon returns `{output:"<decoded status>",
   scope:"partition(startcol=3)/tile(0,3)/mm2s0"}`.
6. Browser appends the decoded status to the console and sets the breadcrumb.

## 7. Failure modes & guarantees

| Situation | Behavior |
|-----------|----------|
| Daemon not running (static HTML opened from disk) | `fetch` rejects → console prints `daemon offline (static mode)`. |
| `aiedbg` not in PATH / no target | Navigation, `help`, `?` still work; live reads return an aiediag "unreachable"/"timed out" string — the REPL and daemon stay alive. |
| A bad command raises in `run_line` | Caught in `serve_stdin`; prints `error: ..`; marker still emitted; server survives. |
| aiegdb subprocess dies | `_gdb_read_until_marker` sees EOF, marks it dead; next `gdb_command` respawns it. |
| Broken stdin pipe | `gdb_command` catches `BrokenPipeError`, drops the proc, returns a retry note. |
| Read hangs | `_gdb_read_until_marker(timeout=60)` returns a timeout note rather than blocking forever. |
| Edited `aiegdb.py`/`aiediag.py` | Click **Reload aiegdb.py** → respawn picks up the new code; scope resets to partition. |

## 9. Design notes / non-goals

- **One subprocess per daemon.** `/aiegdb` calls are serialized by `_gdb_lock`;
  concurrent `/applog`/`/grid` polling is unaffected (separate threads).
- **No new dependencies** — stdlib `subprocess`/`threading`/`queue` only.
- **Read-only by default.** The console cannot stop/reset/write the target
  (except the explicit `dma counter setup`), so it is safe alongside a live
  `apppaltest -nonreboot` session on the same JTAG bridge.
- **The static HTML still works offline** — with no daemon, the console degrades
  to a "daemon offline" message; the schedule view itself is fully usable.
- `/cmd` (the old fixed op-whitelist) remains for backward compatibility but is
  superseded by `/aiegdb` from the UI.

## 10. The LLM tab — embedded Claude Code

The bottom-right command console is **tabbed**: `[aiegdb] [LLM]`. The **LLM** tab
embeds a full, tool-enabled, repo-aware Claude Code agent so the user can chat
about the schedule, the `applog`, or the codebase — with realtime streaming
responses — all over the same daemon. It reuses the exact aiegdb pattern:
a persistent subprocess + a reader thread, plus the applog-tail polling idiom.

### 10.1 Why a headless streaming subprocess (not `claude server web`)

There is **no** `claude server web` command; Claude Code has no built-in web
server. Instead the daemon drives the CLI in **headless streaming mode** and
bridges it to the browser, mirroring how it drives `aiegdb.py --server`:

```
claude -p --input-format stream-json --output-format stream-json \
       --include-partial-messages --verbose \
       --permission-mode bypassPermissions [--model <model>]
```

- **cwd = repo root** → the subprocess loads `CLAUDE.md`, skills, and sees the
  whole codebase, so answers are project-aware.
- **Input:** one JSON line per user turn on stdin:
  `{"type":"user","message":{"role":"user","content":[{"type":"text","text":"..."}]}}`
- **Output:** a JSON-line stream. Assistant text arrives incrementally via
  `stream_event` → `content_block_delta.text_delta`; tool calls appear as
  `assistant` messages with `tool_use` blocks; tool results as `user` messages
  with `tool_result` blocks; each turn ends with a `{"type":"result",...}` line.
- **Auth:** uses the machine's existing Claude login (`/usr/local/bin/claude`).
- The process stays **alive across turns**, so the conversation is multi-turn.

### 10.2 Tiers

```
Browser LLM tab  ── POST /llm {prompt} ─────►  daemon writes 1 JSON line to claude stdin
Browser LLM tab  ── GET  /llm/poll?offset=N ►  daemon returns transcript slice + turn_active
Browser LLM tab  ── POST /llm/reset ────────►  daemon kill+respawn (new conversation)
```

The reader thread decodes each stdout JSON line and appends readable text to an
in-memory buffer (`_llm_buf`); `/llm/poll` returns `{data: _llm_buf[offset:],
next, active}`; the browser polls until `active === false` — exactly the
`/applog?offset=N` tail pattern used for the run console.

### 10.3 Daemon — `DebugState` LLM members (`schedule_debug_server.py`)

| Member | Role |
|--------|------|
| `_llm_spawn()` | `Popen([claude ...streaming...], cwd=repo_root, stdin/stdout=PIPE, text, bufsize=1)` + reader thread that parses each JSON line via `_llm_handle_event`. |
| `_llm_handle_event(obj)` | `text_delta` → raw text; `tool_use` → `\n[tool: <name> <compact input>]`; `tool_result` → `\n[tool result]`; `result` → clear `_llm_active`. Non-JSON lines are skipped. |
| `llm_send(prompt)` | spawn if dead; set `_llm_active=True`; write the user JSON line + flush; return `{ok, offset}` (current buffer length). |
| `llm_poll(offset)` | return `{data: _llm_buf[offset:], next, active}`. |
| `llm_reset()` | terminate + respawn; clear the buffer; return `{ok}`. |

Config fields: `claude_bin` (default `"claude"`), `claude_cwd` (default repo
root = `os.path.dirname(_SCRIPT_DIR)`), `claude_model` (default → CLI default),
`llm_enabled`. All access is serialized by `self._llm_lock`.

To avoid duplicating streamed text, the reader emits **text only** from
`stream_event` deltas and **tool markers only** from the `assistant` message's
`tool_use` blocks (whose text was already streamed).

### 10.4 Routes (`Handler`)

| Route | Handler | Notes |
|-------|---------|-------|
| `POST /llm` | `st.llm_send(body["prompt"])` | No `_hw_available` gate — the LLM tab works with no JTAG board. `404` when `--no-llm`. `401 {auth:true}` when a password is set and `X-LLM-Auth` is missing/wrong. |
| `GET /llm/poll?offset=N` | `st.llm_poll(N)` | Returns the transcript slice + `active`. `404` when `--no-llm`. `401 {auth:true}` when unauthorized. |
| `POST /llm/reset` | `st.llm_reset()` | New conversation. `404` when `--no-llm`. `401 {auth:true}` when unauthorized. |
| `GET /llm/auth` | `st.llm_auth_required()` | **Unprotected.** Returns `{"required": bool}` so the browser knows whether to prompt for a password. |

**LLM auth** (LLM endpoints only; all other routes stay open): set a password
via `--password` (or env `SCHEDULE_DEBUG_PASSWORD`). When set, `/llm`,
`/llm/reset`, and `/llm/poll` require the password in the `X-LLM-Auth` request
header (checked with `hmac.compare_digest`); no password => auth disabled
(backward compatible). The browser stores the password in `sessionStorage`
(`LLM_AUTH`, cleared on tab close) and `api()` attaches it as `X-LLM-Auth`.

On daemon shutdown (`KeyboardInterrupt`) the claude subprocess is also
terminated (alongside the aiegdb subprocess).

### 10.5 CLI flags (`main()`)

| Flag | Default | Purpose |
|------|---------|---------|
| `--claude-bin` | `claude` | Path to the claude CLI. |
| `--claude-model` | none | Model for the LLM tab (else CLI default). |
| `--claude-cwd` | repo root | Working dir so the subprocess loads `CLAUDE.md`/skills. |
| `--no-llm` | off | Disable the LLM tab and its `/llm*` endpoints. |
| `--password` | none (env `SCHEDULE_DEBUG_PASSWORD`) | Password required to use the LLM tab. If unset and stdin is a TTY, the daemon **prompts at startup** (`getpass`, no echo); pressing Enter with no input => no auth. |
| `--no-password` | off | Skip the startup prompt entirely (no LLM auth). |

Startup prints an `LLM: claude found/NOT FOUND (bin=…, cwd=…, model=…)` line (or
`LLM: disabled (--no-llm)`), plus `LLM auth: enabled/disabled` (never the
password itself).

### 10.6 Browser — LLM console (`schedule_view.py` → `host_schedule.html`)

- A `#contabs` bar switches `.hide`/`.act` between `#conpane` (aiegdb) and
  `#llmpane` (LLM). `#llmpane` has an output `<pre id="llmout">`, an input row
  (`#llmin` + **Send**), and a **New chat** (`#llmreset`) button — styled to
  mirror `#conterm/#conout/#conin`.
- `llmSend(prompt)` echoes `you> prompt`, POSTs `/llm`, then starts `llmPoll`.
- `llmPollOnce()` GETs `/llm/poll?offset=N`, appends `data`, advances the
  offset, and stops when `active === false` (reentrancy guarded by a busy flag),
  reusing the applog poll idiom.
- `llmReset()` POSTs `/llm/reset` and clears `#llmout`.
- Enter-to-send on `#llmin`; click-to-focus on `#llmterm`.
- **Reveal logic:** the LLM tab is independent of the JTAG "Test connect". On
  load (over `http:`) the page probes `GET /llm/poll?offset=0`; if the daemon
  answers (and the tab is enabled), it un-hides `#cmdconsole` + `#rhsplitter` and
  default-selects the **LLM** tab. The aiegdb tab stays gated on
  `LIVE.connected`. On `file://` (no daemon) the probe fails and the page stays
  in static mode.

### 10.7 Security note

`--permission-mode bypassPermissions` gives the browser-driven Claude **full
tool access** in the repo (read/write/exec). The daemon binds `0.0.0.0` by
default, so:

- Run with `--host 127.0.0.1` (localhost-only) or behind a trusted network.
- Use `--no-llm` to disable the LLM tab and its endpoints entirely.
- To require a password before the browser may talk to the LLM subprocess,
  either pass `--password`/env `SCHEDULE_DEBUG_PASSWORD`, or just start the
  daemon in a terminal: it prompts `LLM chat password (press Enter for no
  password)` at startup (Enter => no auth; `--no-password` skips the prompt).
  The browser prompts with a modal on the LLM tab, stores the password in
  `sessionStorage`, and sends it as the `X-LLM-Auth` header; a `401` re-locks the
  tab. Only the `/llm*` endpoints are gated — the schedule/run/debug endpoints
  stay open.

## 11. MCP tier — `src/tool/debug/aiemcp.py`

A **third front-end** onto the same `AieGdb.run_line` dispatch, this time for an
MCP client (Claude Code). Unlike the daemon tier (§3), which drives
`aiegdb.py --server` over a pipe framed by `_SERVER_MARKER`, the MCP server
imports `aiegdb.AieGdb` **in-process** and keeps one long-lived instance whose
scope (partition → tile → channel) persists across MCP tool calls.

```
┌─────────────────────────────────────────────────────────────────────────┐
│  MCP client  —  Claude Code   (auto-discovers server from .mcp.json)      │
│    tools: aie_exec / aie_scope / aie_commands / aie_help                   │
└───────────────┬───────────────────────────────────────────────────────────┘
                │  MCP JSON-RPC over stdio (fd 0/1)
                v
┌─────────────────────────────────────────────────────────────────────────┐
│  MCP server  —  src/tool/debug/aiemcp.py   (FastMCP, stdio)                        │
│    ONE in-process AieGdb; _run() dup2-captures fd 1/2 around run_line()    │
│    config from env: AIEDBG_TARGET, AIEMCP_DEVICE/STARTCOL/AIE_VERSION/..   │
└───────────────┬───────────────────────────────────────────────────────────┘
                │  same run_line() dispatch  →  aiediag  →  aiedbg  →  board
                v
                (§5 tier — unchanged)
```

### 11.1 Tools

| Tool | Console equivalent | Purpose |
|------|--------------------|---------|
| `aie_exec(cmd)` | any `run_line` | Run one command line; primary tool. |
| `aie_scope()`   | `where` | Current scope + config. |
| `aie_commands()`| `?`     | Commands valid at the current scope (discovery). |
| `aie_help()`    | `help`  | Full command reference. |

Each returns `{"output", "scope"}` (except `aie_help`, a plain string), where
`scope` is the post-command prompt so the client can track the breadcrumb.

### 11.2 stdout is the MCP channel (the critical constraint)

FastMCP stdio uses **fd 1** for JSON-RPC, but `aiegdb` prints results to stdout
*and* `AieGdb._passthrough` runs `subprocess.run(cmd)` **without capture**, so a
child `aiedbg` writes to the inherited fd 1. `contextlib.redirect_stdout` alone
would not catch the child. `_run()` therefore does **OS-fd-level** capture: it
`dup2`s fd 1/2 to an `os.pipe()` (also repointing `sys.stdout`/`sys.stderr`),
calls `run_line()`, restores the saved fds, then drains the pipe. A single
`threading.Lock` serializes the fd swap so calls cannot interleave.

### 11.3 Fault tolerance

`aiediag.run_aiedbg_reg_read` calls `sys.exit(1)` when `aiedbg` is missing.
`_run()` wraps `run_line()` in `try/except (SystemExit, Exception)` so a missing
board/binary returns an error string in `output` and the server stays alive.
ANSI codes are stripped defensively (aiediag already disables color off-tty).

### 11.4 Configuration & registration

MCP servers launch via `.mcp.json`, not argv, so config comes from env vars:
`AIEDBG_TARGET` (falls back to `~/.aiedbg_env`), `AIEMCP_DEVICE`,
`AIEMCP_STARTCOL`, `AIEMCP_AIE_VERSION`, `AIEMCP_JSON_DIR`, `AIEMCP_DRY_RUN`.
Unset `startcol`/`aie_version` are auto-resolved from provenance JSON exactly as
`aiegdb.main()`. The repo-root `.mcp.json` registers the server as `aiegdb`
(`python3 src/tool/debug/aiemcp.py`); Claude Code auto-discovers it on start.

Dependency: the `mcp` Python SDK (`pip install "mcp[cli]"`); no other new deps.
Dry-run the whole flow with **no** hardware: `AIEMCP_DRY_RUN=1 mcp dev
src/tool/debug/aiemcp.py`.

### 11.5 Non-goals

The MCP server only *drives* `aiegdb`/`aiediag` — it adds no new hardware write
paths (read-only except the existing explicit `dma counter setup`, reachable via
`aie_exec` just as in the CLI) and does not modify their behavior.
